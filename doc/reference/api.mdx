The full public API of Agent SDK. Plugins use only what's on this page.

```lua
local sdk = require("agent_sdk")
```

## Setup

`sdk.setup({ adapters = { ... } })` registers the user's adapters. Plugins don't call it, except in tests. See [Configure adapters](/configure/adapters).

An adapter in `setup()` with `base = "name"` copies that built-in adapter and overrides any part of it. One without `base` is a complete adapter, used as it is.

## Adapters

`sdk.adapter(name)` returns the user's adapter, or `nil, err` with an error the plugin can show the user.

| Field | |
| --- | --- |
| `adapter.name` | The user's name for it |
| `adapter.type` | `"http"` or `"acp"` |
| `adapter.capabilities` | Read-only. `tools`, `vision`, `reasoning` (booleans) and `models` (a list) |
| `adapter:has_model(model)` | `false` only when the adapter knows its models and `model` isn't one of them |

`capabilities.models` is empty until the SDK knows the models. For an ACP agent, that's once a session has started. `has_model()` never returns `false` for a model it can't check yet, so a plugin never warns the user wrongly.

## Sessions

```lua
local session = sdk.session({
  adapter = adapter, -- from sdk.adapter()
  mode = "plan", -- optional, ACP agents only
  model = "claude-opus-5", -- optional, nil keeps the user's default
  on = { ... }, -- handlers for every prompt in the session
  system_prompt = "...", -- optional
  thought_level = "high", -- optional, see /reference/adapters
  tools = { ... }, -- optional, the tools the model can call, see /reference/tool-calls
})
```

`sdk.session()` returns straight away. Nothing is sent until the first prompt.

| Call | |
| --- | --- |
| `session:prompt(content, opts)` | Sends a prompt and returns a `vim.async` task. Closing the task stops the reply |
| `session:ask(content, opts)` | The same, inside a `vim.async` task. Returns `reply, err` |
| `session:close()` | Stops any reply in progress and ends the session. For ACP, stops the agent's process |
| `session.messages` | The history, read-only. On ACP, a record of what the SDK saw |
| `session.tools` | The session's tools, read-only |
| `session:set_messages(messages)` | Replaces the history and returns `true`. On ACP, changes nothing and returns `false, err` |

`content` is a string, or a list of blocks like `{ type = "text", text = "..." }`.

`opts`:

- `stream`: `false` runs every handler in one burst once the reply is complete. A reply with a tool call arrives as one burst up to the tool call, and another once the call is answered. Defaults to `true`
- `on`: [handlers](#handlers) for this prompt only. Each replaces the session's handler of the same name

## Handlers

Handlers go in `on`, for every prompt in a session, or in a prompt's `opts.on`, for that prompt only. Every handler receives one table, `data`. New to these ideas? See [Core concepts](/concepts).

```lua
on = {
  text = function(data) end,
  reasoning = function(data) end,
  usage = function(data) end,
  tool_update = function(data) end,
  done = function(data) end,
  error = function(data) end,
  request = {
    tool_call = function(data) end,
    permission = function(data) end,
  },
}
```

The handlers under `on.request` ask your plugin for something, and the reply waits until the handler answers. The rest only tell your plugin something.

### text

A piece of the answer, as it [streams](/concepts#streaming).

| Field | |
| --- | --- |
| `data.text` | The piece of text |

### reasoning

A piece of the model's [reasoning](/concepts#reasoning). Not every model or adapter produces it.

| Field | |
| --- | --- |
| `data.text` | The piece of reasoning |

### usage

Token counts, once per request.

| Field | |
| --- | --- |
| `data.input_tokens` | Tokens sent to the model |
| `data.output_tokens` | Tokens the model wrote |

### tool_update

The progress of a [tool call](/reference/tool-calls). On HTTP, sent when your plugin answers the call.

| Field | |
| --- | --- |
| `data.id` | The tool call's id |
| `data.status` | `pending`, `in_progress`, `completed` or `failed` |
| `data.output` | The tool's output |

On ACP, also `title`, `kind`, `content`, `locations`, `arguments` and `meta`.

### done

The whole reply, once it's complete.

| Field | |
| --- | --- |
| `data.text` | The answer |
| `data.reasoning` | The reasoning, if any |
| `data.tool_calls` | Every tool call in the prompt, with its latest `status` and `output` |
| `data.usage` | Token counts for the whole prompt |

### error

The prompt failed or was stopped. See [Failed prompts](/reference/sessions#failed-prompts).

| Field | |
| --- | --- |
| `data.message` | What went wrong |
| `data.cancelled` | `true` when your plugin stopped the reply |
| `data.prompt` | What was passed to `session:prompt()` |

### request.tool_call

The model asks your plugin to run a tool. See [Tool calls](/reference/tool-calls).

| Field | |
| --- | --- |
| `data.id` | The call's id |
| `data.name` | The tool's name. `nil` on ACP, which has no tool names |
| `data.arguments` | The tool's arguments |
| `data.needs_result` | `true` when your plugin must answer |
| `data.respond(content)` | Answers with the tool's result |
| `data.fail(message)` | Answers with an error |

On ACP, use `data.title` and `data.kind` in place of the name, `data.status`, and `data.meta` for the agent's own extras.

### request.permission

An agent asks before it acts. See [Permissions](/reference/permissions).

| Field | |
| --- | --- |
| `data.tool_call` | What the agent wants to do, with `id`, `title` and `kind` |
| `data.options` | The answers on offer, each with `id`, `name` and `kind` |
| `data.respond(option_id)` | Answers with one option's `id`. `nil` cancels |

### Kinds

`kind` fields use ACP's values:

- **Tool kinds:** `read`, `edit`, `delete`, `move`, `search`, `execute`, `think`, `fetch`, `other`
- **Option kinds:** `allow_once`, `allow_always`, `reject_once`, `reject_always`

## Rules

- Handlers run on the main loop, so they can write to buffers and windows directly
- Every prompt ends with exactly one `done` or one `error`
- Stopping a reply ends the prompt with an `error` whose `cancelled` is `true`. On HTTP, nothing from the stopped reply is added to the history
- A prompt that ends in `error` adds nothing to the history, not even the prompt itself. `data.prompt` holds what was passed to `session:prompt()`, so the plugin can send it again or return it to the user
- Calling `session:prompt()` or `session:ask()` while a reply is in progress raises an error
- An `on.request.permission` handler must call `data.respond()`. The agent waits until it does. `data.respond(nil)` cancels
- Without an `on.request.permission` handler, the SDK picks the agent's reject option, or cancels the request when the agent offers none
- An `on.request.tool_call` handler must call `data.respond()` or `data.fail()` when `data.needs_result` is `true`. The prompt carries on once every call is answered, and ends in one `done`. Without one, the SDK fails every call
- The SDK closes every open session on `VimLeavePre`

## Test adapter

```lua
local scripted = require("agent_sdk.test").adapter({
  type = "acp", -- optional, defaults to "http"
  replies = {
    -- one list per request, each ending in done or error
    {
      { type = "text", text = "Hello" },
      { type = "done" },
    },
  },
})
```

`scripted.responses` lists the option ids the plugin's permission handlers responded with, in order. See [Test adapter](/reference/test-adapter).
